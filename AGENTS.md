# Agent guidelines

This repository is the public Kotlin Swift Export sample. It shows how Kotlin Multiplatform code is exported to Swift with the `export.swift {}` DSL and the Swift package export from Kotlin 2.5.0. People read it to learn Swift Export, so the code has to be correct, small and easy to follow.

Read `README.md` first. It explains the project structure, the DSL and every language feature the sample covers.

## Layout

- `shared/` - The umbrella Kotlin module, exported as the `Shared` Swift module. Its API in `src/commonMain/kotlin/com/github/jetbrains/swiftexport/` is split into one file per language feature.
- `module-a/` to `module-d/` - Kotlin libraries that show the different ways a dependency is exported (library-configured, consumer-configured, `EXPOSED`, `HIDDEN`).
- `appleApp/` - A SwiftUI app for iOS and macOS that consumes the Kotlin code through `embedSwiftExportForXcode`. One multiplatform target (`appleApp`) and one hosted XCTest target (`Tests`).
- `spm-consumer/` - A Swift package that consumes the exported Swift package. Its Swift Testing tests are the main language feature tests.
- `shared/SwiftPackage/` - Generated by the export tasks and git-ignored. Never edit it.

## Verifying a change

Run what your change touches. A change to the Kotlin API touches all three.

```shell
# Swift package export and the Swift Testing tests (macOS)
./gradlew :shared:exportDebugSwiftPackage
swift test --package-path spm-consumer
swift run --package-path spm-consumer

# The app and its XCTests, on both platforms
xcodebuild test -project appleApp/appleApp.xcodeproj -scheme appleApp -destination 'platform=macOS,arch=arm64'
xcodebuild test -project appleApp/appleApp.xcodeproj -scheme appleApp -destination 'platform=iOS Simulator,name=<an available iPhone simulator>'
```

`swift test` uses the package from the last export, so export again after every Kotlin change. The Xcode build runs Gradle itself through the Run Script phase.

Before you write Swift code against a Kotlin declaration, read its generated signature in `shared/SwiftPackage/Debug/Sources/<Module>/<Module>.swift`. Argument labels, optionality and namespaces are easy to guess wrong.

## Adding a Swift Export feature

1. Add the Kotlin declarations to the matching topic file in `shared/` (or a new one), with a short comment that says what Swift gets.
2. Test it from Swift in `spm-consumer/Tests/SwiftExportTests/` and in `appleApp/Tests/Tests.swift`.
3. If it is visible in a UI, add a row to the matching section in `appleApp/appleApp/ContentView.swift`.
4. Update the language feature table in `README.md`, and the known limitations if the feature has one.

The Xcode project uses buildable folders, so new Swift files in `appleApp/appleApp/` or `appleApp/Tests/` are picked up without editing `project.pbxproj`.

## Swift Export pitfalls

- The sample targets the Kotlin version in `gradle/libs.versions.toml` (currently 2.5.0-Beta2). Swift Export changes quickly, and a feature on Kotlin `master` may not exist in that version yet. Check before you use it.
- Kotlin can't call Swift-only APIs. When Kotlin needs one, declare a function type or an interface in Kotlin and let Swift provide the implementation (see `FunctionTypes.kt`).
- Swift package export can't be combined with `swiftPMDependencies {}` in Kotlin 2.5.0. Support is planned for Kotlin 2.5.20.
- A Swift class that implements a Kotlin interface must inherit from an exported Kotlin class, because `KotlinBase` can't be instantiated from Swift (KT-88251).
- Passing a Swift dictionary to a Kotlin parameter of type `Any` crashes with SIGSEGV in 2.5.0-Beta2. Don't add it to the samples.
- Declarations that need an opt-in in Kotlin are Swift SPI: `@_spi(<annotation FQN with $ instead of dots>) import Shared`.
- Swift names can clash with SDK names. SwiftUI declares `Shape`, so the app writes `Shared.Shape`.

## Xcode project rules

- `MemberImportVisibility` is on. Import every module whose members a file uses. Members inherited from Kotlin stdlib classes, such as `Throwable.message`, need `import KotlinStdlib`, and stubs of the hidden `:module-d` need `import ModuleD`.
- Keep `SWIFT_DEFAULT_ACTOR_ISOLATION` unset. The generated Kotlin declarations are nonisolated, so with main actor isolation every Swift override of a Kotlin member fails to compile.
- Keep `ENABLE_USER_SCRIPT_SANDBOXING = NO` on the `appleApp` target. The Run Script phase runs Gradle, which reads and writes outside the sandbox.
- iOS-only API (UIKit, `iosMain` declarations) must be behind `#if os(iOS)`, because the same target builds for macOS.
- Attach sheets and other presentations outside the lazy `List`. A presentation attached to a `List` section is dismissed when the List rebuilds that section.
- Kotlin objects are not observable. Keep Kotlin results that drive the UI in `@State`, and keep frequently changing state in the smallest view that uses it.

## Writing style

- Comments and docs are short and plain. Say what Swift sees, not how impressive it is.
- Keep `README.md` in sync with the code. Every claim in it should be something the sample shows or a test checks.
- Use small, focused commits with a short imperative subject, for example "Add macOS destination to the Xcode app".
